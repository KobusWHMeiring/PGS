How to use this

Part 1 and Part 2 are the answer to “what will MVP 0 be”. Part 3 records five defects found while checking the plan against the source documents — these are fixes, not choices. Part 4 holds the open questions; each needs a decision from you (or the group) before the plan is rewritten.

Pick an option on each question card and add notes. Everything autosaves in this browser. The Export decisions button produces a markdown decision log you can paste into the spec’s §18 decision table or attach to the plan.

Nothing here is a certification claim. MVP 0 ships a public site and a standards chatbot. It publishes no farm status, no certificate, no seal and no QR code — by design.

Part 1 — What MVP 0 is

One sentence, then the reasoning, then the fence.

In one line

A public website for the group, and a grounded chatbot that answers only from the four governing documents — citing them, and refusing when they don’t cover the question.

No accounts. No farm records. No certificates. No assessor app. No claim of any kind about any farm.

Why this slice goes first

Three reasons, in order of weight.

Reason What it retires
It proves the clause model the assessment templates depend on. The FORM’s verdicts are derived from SAOSO clauses (V1a (S20.1.1)). If ingestion cannot produce reliable clause references from the real PDFs, MVP 1’s frozen template snapshots and MVP 3’s gap analysis are both built on sand. Better to find that out in week two than week twenty.
It proves the chatbot can say “I don’t know”. The group’s trust in the whole platform is staked on the bot not inventing standards. That is a judgement no test can make — it needs a real user reading a real answer (UAT Scenario 1).
It is the feedback surface the group needs before it hands over certification records. They can see and use a marketing site and a chatbot immediately. They cannot evaluate a sync protocol until it has carried a real visit.
⚑

Why it is emphatically not the registry. Publishing certification status before the machinery that substantiates it exists is the one move that could damage the group’s credibility — precisely the problem a PGS exists to solve. The registry lands in MVP 2, behind real certificate data. MVP 0 makes no claim, so it cannot make a false one.

Part 2 — What gets built

Four sub-plans from MVP0_PLAN.md, each with the one thing it must prove.

A

Foundation

A deployable, empty, health-checked Django 5.2 monolith with CI, off-box backup and the one-way import rule enforced by tooling.

Deliverables

Repo scaffold + requirements.txt · env-driven settings (.env only) · custom User with plural UserRole · Category and Seal tables + seed_deployment · /health/ checking DB, Redis, broker, worker · Celery with retry policies · .importlinter contract · pytest + Playwright + git CI · backup.sh / restore.sh + docs/RUNBOOK.md.

Proves: the deploy target exists and a restore has actually been rehearsed — not assumed.

B

Standards corpus & retrieval

ingest_standard loads the real PDFs; retrieval returns citable chunks, scoped before ranking.

Deliverables

StandardSet / StandardDocument / DocumentChunk with pgvector + generated tsvector · pluggable section parsers selected by data · heading-boundary chunker (~800 tokens, overlap) · Gemini embeddings with an explicit timeout · idempotent re-ingest on sha256 · hybrid FTS + vector fused by RRF, optionally reranked.

Proves: the clause model works on the documents that exist — see Part 3, which is where this sub-plan currently fails.

C

Public site & documents

The group’s public surface, hosted by the platform, making no claim.

Deliverables

Marketing pages in the group’s own voice · six basic elements from LANDSCAPE · fee schedule from OPP §II · member list carrying the “membership is not certification” disclaimer (an OPP requirement, not a nicety) · /documents/ with stable URLs · bilingual scaffolding · vendored HTMX only where it earns its place.

Proves: the WordPress site can be retired, and the Drive dependency with it.

D

Grounded chatbot

answer_question() with a strict JSON contract, mandatory citations and a structured escalation.

Deliverables

Gemini with response_mime_type="application/json" and a fixed schema (answer, citations[], insufficient_context) · refusal triggered on the flag, not on prose · citation validity check against the retrieved set · EscalatedQuery for administrative follow-up · per-IP rate limiting, 500-char cap, answer cache, token accounting.

Proves: the bot answers from the standard, cites something findable, and refuses convincingly — the three judgements in UAT Scenarios 1–3.

Part 3 — What must be fixed first

Five defects found by extracting text from the actual PDFs and workbook and checking the plan against it. These are not open questions — the fix is clear. They are listed because two of them make MVP 0 silently ship a broken corpus.

⛔

F1 and F2 are P0. As written, ingestion produces zero section references from SAOSO and cannot cite the OPP’s seals or aggregation sections at all. The plan’s own tests pass against hand-written fixtures in the invented format, so CI stays green while the chatbot has nothing to cite.

F1

The SAOSO parser matches nothing

Spec §4.5 and §13, MVP0_PLAN.md Task B2 and the UAT all assert SAOSO cites clauses as B-20.1.1. SAOSO does not.

Actual text, saoso-version-2.1-2026.pdf 
SECTION B
20.1. General
20.1.1. Handlers and processors shall not co-mingle organic
         products with non-organic products.
20.1.2. Handlers and processers shall ensure traceability in
         the organic processing and handling chain.

grep -cE '^[A-Z]-[0-9]' saoso-version-2.1-2026.txt   →  0
Fix

Rewrite _CLAUSE for ^\s*(\d{1,2}(?:\.\d{1,2})*)\.\s and capture the enclosing SECTION A/B/C for disambiguation — 1.1.1 exists in both Section A and Section B, so a bare reference is ambiguous. Fix _APPENDIX for the real forms: Appendix 1., Appendix 4. Table 1, Appendix 6a.

Then add the test that was missing: assert ingestion of each real PDF yields more than zero sections with a non-empty section_ref. Fixtures must be verbatim extracts of the shipped PDFs, never hand-written strings.

F2

The OPP parser cannot cite the seals or the aggregation sections

The spec cites OPP §I, §II, §V, §VI, §VII throughout — including the whole traceability appendix. The parser’s heading regex requires digits, so Roman-numeral sections never match.

Unreachable by the plan's parser 
I.   Membership procedure
II.  Membership fees, farm assessment fees, licensing fees
V.   Seals and certificates issued by the PGS committee     ← the seals
VI.  Aggregation of produce within the PGS                  ← the aggregation
VIII. PGS bank account and signatories
Fix

Add a Roman-numeral top-level rule and nest the numbered subsections under it. Both domain areas the review added live in sections the parser cannot reach — so the chatbot cannot cite the OPP for exactly the claims most worth citing. Related: §4.2(5) and §4.1.2 are numbered list items, not headings, and need a sub_ref field (Q2).

F3

§12 contradicts the decision log and the UAT on the pasture-raised seal

§4.3 and D11 say the seal is not shipped, seeded is_active=False. §12 says the platform “renders the pasture-raised seal with its undefined-criteria caveat”. The UAT’s automated suite is specified to fail if rendered public HTML contains the string pasture raised.

Fix

Delete the §12 sentence. The seal stays inactive and is never rendered; issuance is hard-blocked when is_active=False (the spec currently leaves that ambiguous). “GMO free” stays treated as a producer statement, never an endorsement.

F4

“Notifiable exception” is defined backwards

Spec §2: “A deviation that must be reported to PGS SA.” Three source documents say the opposite — it is an exemption granted, documented and reported.

Source text 
FORM Sheet I §3   "Indicate any notifiable exception as allowed in the
                  organic standards granted and notify PGS SA"
OPP §V            "The PGS has the authority to grant notifiable
                  exemptions to the standards, which must be well documented."
BPP, Intro        "The Standard describes ... various technical
                  specifications and notifiable exceptions."
Fix

Not an MVP 0 model, but it changes §2 and §4.2. Drop Finding.is_notifiable_exception; add a NotifiableExemption record with clause, rationale, granted_by, granted_on, reported_on, document reference. Do it before the question templates encode the wrong definition.

F5

The repo is untracked inside another git repository

Task A1 begins with git init. That creates a nested repository — but pgs/ currently sits untracked inside a repo rooted at ~/Documents/Dev, which holds ~30 unrelated projects and has no .gitignore.

Current state 
git rev-parse --show-toplevel  →  C:/Users/…/Documents/Dev
git ls-files .                 →  (empty)
cat ../.gitignore               →  (absent)
Fix

Before any spec edit is committed: git init inside pgs/, make the first commit, and add pgs/ to Dev/.gitignore so a stray git add -A from the parent cannot swallow this project along with twenty-nine others.

Part 4 — Open questions

Q1–Q8 block the plan. Q9–Q11 block launch but can be settled in parallel. Each card carries a recommendation; anything you pick is recorded.

Q1

What is the canonical citation format for SAOSO clauses?

Three conventions are in play. SAOSO’s body prints 20.1.1.; the FORM cites S20.1.1; the spec invented B-20.1.1. The choice decides the parser, the section_ref contract, and what a citation looks like to a farmer.

Recommendation

Match the FORM: S20.1.1. The group already reads and writes this on paper, and every verdict in the workbook will carry a reference a committee member can find. Store the section letter separately for disambiguation. Render as “SAOSO §20.1.1 – Processing Handling”.

Q2

How deep must citations go for the OPP?

The spec cites §V (seals) and §4.2(5) (the five-day conclusion window). The second is a numbered list item inside a subsection — it needs structured parsing, not a heading regex, and it is the granularity the load-bearing rules actually use.

Recommendation

Two-level: section reference plus optional sub_ref. Guarantee §V and §4.2 everywhere; populate sub_ref for the enumerated rules the spec depends on (5-day notice, 3-day questionnaire, 5-day conclusion, paid-up gate, Critical-action escalation). Do not attempt every list item — capture the six that carry rules.

Q3

Which documents are in the chatbot’s corpus?

Sub-plan B says “the four real PDFs”. §13 says “SAOSO … and the Outeniqua SOPs / OPP / BPP” — which reads as three or four depending on whether “SOPs” is a separate document. /documents/ hosts eight. These are different numbers for different jobs.

Recommendation

Corpus = four: SAOSO, OPP, BPP, LANDSCAPE. One StandardSet. The assessment workbook and the three participant checklists are /documents/ downloads only — the workbook is a form, not a standard, and ingesting it would let the bot cite its own questionnaire. Note the OPP contains the SOPs, so “OPP” and “SOPs” are one document.

Q4

Does the chatbot answer about the SAOSO standard only, or about the group’s own rules too?

The refusal string is fixed as “I cannot find a definitive answer in the SAOSO standards.” But the corpus includes the OPP — which answers questions the SAOSO standard does not, like “how much is membership?” and “how do I join?”. The fixed wording may misdescribe what the bot actually does.

Recommendation

Keep the corpus wide, fix the wording. Answer from all four documents, and change the refusal to name the group: “I cannot find a definitive answer in the SAOSO standard or the Outeniqua PGS documents.” The old string was preserved for UX stability out of the original PRD, which had only SAOSO in scope.

Q5

How much Afrikaans does MVP 0 actually ship?

D7 makes English and Afrikaans both first-class. UAT Scenario 5 says machine-translated Afrikaans “would undercut the site’s credibility more than leaving it in English would”. Those two statements cannot both be satisfied without a human translator — and nobody is named.

Recommendation

Ship the mechanism, not the translation. preferred_language, the catalogue plumbing, and one small human-translated shell (navigation, form labels, the chatbot frame). Page content and chatbot answers stay English until a named Afrikaans-speaking member reviews them. Then Scenario 5 is judged against a real translation, not a machine one.

Q6

Where does MVP 0 run?

The handover records hosting as “not decided anywhere”. Sub-plan A ends with a backup script that assumes an attached drive, and there is no docker-compose.yml. Two constraints narrow the field: pgvector must be installed, and the media volume needs an attached backup target.

Recommendation

A single small VPS with Docker Compose; backups to a drive held by the group. pgvector rules out shared hosting. The backup target must be off the box and its failure must be alertable — R11 is the spec’s highest-severity risk, and it is only accepted because someone knows about it.

Q7

Whose Gemini key, and what is the monthly ceiling?

D3 chose Gemini. The spec requires per-IP rate limiting, a question cap, answer caching and “spend alerting” (R9) — but no budget or owner is recorded, and embeddings for the whole corpus are one-off spend that must happen before Scenario 1 can be tested at all.

Recommendation

Group-owned account, hard monthly cap, alerting at 50%. Note D3’s consequence: the embedding dimension is frozen in the migration, so changing the model later means re-embedding the entire corpus. Pick the model deliberately now, not by default.

Q8

Does MVP 0 replace the live WordPress site, or ship as a preview?

D8 says “this application is the PGS Outeniqua website; the WordPress site is retired, not run alongside it.” But MVP 0 has no registry, so retiring WordPress at MVP 0 would drop the group’s existing farm-status pages — the ones that currently carry their certification claims.

Recommendation

Preview at MVP 0; cut over at MVP 2. Ship on a staging domain the group can browse and critique. Retire WordPress only once the registry can carry the farm-status pages it is replacing — otherwise MVP 0 removes information the group currently publishes, which is a regression, not a launch. The redirect map becomes a MVP 2 checklist item.

Q9

May the platform host the workbook and the historical dossiers publicly?

/documents/ retires the Google Drive dependency. But the live site gates some files behind Drive permissions, and historical application dossiers and visit reports are “granted on request” — a permission model, not a public one. Dossiers contain farmer personal data.

Recommendation

Split the list. Publish the standard, BPP, OPP, landscape, prep list and the three blank checklists — those are already effectively public. Keep dossiers permission-gated behind the farmer account (MVP 1), not on a public URL. Get an explicit yes from the committee for the workbook.

Q10

Who signs MVP 0 off?

The UAT’s release gate needs four named humans — Product, PGS administrator, committee reviewer, consumer member. Scenarios 1, 3, 4 and 8 are judgements only those people can make. Three of the four seats are currently blank.

Recommendation

Name them now. If the administrator who will actually use the chatbot is not available to judge Scenarios 1–3, MVP 0 has no meaningful acceptance test and the UAT is theatre.

Q11

Does knowledge/ stay a separate app?

§18.2’s own honest note says the case is narrow and Option A is defensible. Its two stated reasons — “the engine may be swapped” and “enforce with tooling” — do not actually require a separate app, because import-linter works on module paths.

Recommendation

Keep the split, but restate the reason. An app is a migration namespace, and the corpus has an independent lifecycle: re-ingestion, sha256 idempotency, version chains, and a frozen embedding dimension. Corpus migrations should never be entangled with certification migrations. MVP 0 is also where the boundary is free, since the slice is the knowledge app plus a site.

Part 5 — Definition of done

MVP 0 is done when all five hold. Two are machine-checkable, three are not.

Gate Type
Every document ingests with non-empty section references, and a test proves it against the shipped PDFs — not fixtures. Automated · currently missing
The automated suite is green, including claim discipline, retrieval scope, grounding, idempotent re-ingest and the knowledge ↛ core contract. Automated
A restore has been rehearsed from the backup drive onto a clean machine — not assumed. Human · Sub-plan A
All eight UAT scenarios judged acceptable, signed by the four named seats. Human · UAT
No certification claim appears anywhere on the public surface — including tone, headings and the member list — confirmed by the committee, not just by the grep. Human · Scenario 8

Part 6 — What happens after the decisions

  1. Apply F1–F5 to the spec and the plan. Roughly half a day. F1 and F2 change Task B2 and the UAT’s automated row.
  2. Fold Q1–Q8 into PGS_PLATFORM_SPEC.md §18.3 as D14–D21, so the decision log stays the single record. Export this page and attach it.
  3. Re-verify the parsers against the real PDFs in a throwaway script, before the plan is rewritten — twenty minutes that de-risks the whole sub-plan.
  4. Then, and only then, rewrite MVP0_PLAN.md. The sub-plan structure survives; tasks B2, B5 and the settings/backup tasks change.
  5. Move the plan to ready/ with Status: Ready, and git init the repo as step zero of Task A1.
  6. Run the two-day offline spike in parallel with MVP 0’s first week. It is not MVP 0 work, but if it fails, MVP 1 is a rewrite — and you want that answer before six weeks of chatbot work, not after.
