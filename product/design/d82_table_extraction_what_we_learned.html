How to read this

This is a record of what was measured, in order, with the correction that came after it. It is not a proposal and not a status report. Every number here comes from a committed evidence file or a command you can re-run; nothing is estimated unless it says “inferred”.

Part 2 — The shape of the problem

Why this is hard, in one diagram. Three different things have to be right, and different tools get different ones right.

Reading a table is three jobs, not one

1 · Structure

Which printed lines are the header, which are rows, which are dividers, which cells are merged. A layout model does this with geometry; a vision model does it by looking.

2 · Characters

What each cell actually says. An extractive tool copies what is on the page. A generative model writes what it believes it read — a wrong digit looks identical to a right one.

3 · Meaning

Is 1 a row number or a value? Does a label beside a seal belong to the artwork column? Is “South African specific” a row or a qualifier? No general tool knows.

…and one rule that binds them

R3: every cell must be a contiguous run of the printed page, in printed order. That is what makes a quote a quote rather than a plausible reconstruction.

Figure 1 — the loop both arms run. The tool's job is to propose; the page's job is to be the witness; one scorer decides.

0 of 8 as extracted; 1 of 8 if you agree “row 0 is the header”; 2 of 8 tables not detected at all. Rows and columns are usually found — this is not a tool that cannot see. It is a tool whose structure loses header association, spans, dividers, page-break rows and non-text. 163–330 s for the eight pages.

That fired the threshold in decision D81: “Document AI only if Docling loses spans, qualifiers or header association on three or more of the eight.” It loses all three, on more than three. So the plan at that point was: buy a Google Cloud credential.

Investigation 2 · 2026-11-04

The vision model via OpenRouter: 8 of 8 tables found, 2 of 8 read

The other class of tool. No install, no local model — you send page images and a generative model answers. The catalogue that day listed 419 models, of which 276 accept an image and 154 a PDF. Two were measured: gemini-3.1-flash-lite and claude-sonnet-5.5.

But a generative model writes what it believes it read. So it was never asked for text. It was asked for structure, and every character was checked against the page. Three forms were tried, because the rule has three readings:

FormWhat the model returnsWhere the characters come from
lineseach cell's printed lines, copiedthe page, checked line by line
anchorsa cell's first and last wordsthe page, sliced between them
indicesline numbers onlythe page, by construction

48 calls across the three forms, $0.55 in total, 5–10 s per shape. (The two surviving forms are the ones published; the line-number form was measured and dropped.) It found every table (8/8) and got header association right on 7–8 of 8 — the requirement Docling lost completely — and it proposed dividers, which no layout model returns. But the best form passed only 2 of 8.

Two hard limits showed up immediately:

  • Line numbers cannot separate cells. In the extracted text a printed line is a whole row — Below R 250,000 1,500 900 — so no set of line numbers can produce three cells from it. The indices form scored 0 of 8.
  • Anchors need a cell to be contiguous. On Appendix 7 every cell failed, because the page text interleaves four columns. This turned out to be the wrong conclusion — see Investigation 3.
Investigation 3 · 2026-11-04, an hour later

The follow-up that changed the answer: the biggest defect was ours

Three checks, all re-scored from the cached model answers — no new call, so nothing was bought:

3.1 · Would a different pass have helped? No.

Re-scoring the same answer against the pass each shape does not declare: no verdict improved, and three got worse. empty_cells went from 0 to 11 quote violations; page_break_row from 6 to 17; and a passing shape demoted. The pass we already used is the better of the two available.

3.2 · Could a better pass be built? Not from what we have.

Appendix 7's extracted page is decisive: the gap between two columns collapses to a single space when a cell overflows. There is no gutter to split on, so no character-offset de-interleaver can recover the cells. De-interleaving needs per-word geometry, which neither committed pass carries.

Figure 2 — two separate problems in one line of text. The collapsed gap needs geometry. The row number needs a decision.

3.3 · The row number: a declared normalisation

The paper prints a bare row number beside each row. Both arms counted it as data. Declared as a narrow rule — drop a bare leading row number from a row carrying exactly one cell more than the header; a real first column (1 Aeration or oxygenation…) is never touched — Appendix 7 flipped for both arms at once.

Figure 3 — the session, in order. The correction is not a better tool; it is a better reading of what the page prints.

The correction, stated plainly

The single biggest defect found across both arms was a mapping convention, not a tool. That does not make any arm adoptable — its characters still need checking — but it changes which question is worth spending money on.

Two things worth inheriting

An extractive tool's characters are not ours. It re-reads the page rather than using the PDF's text layer: it returned 1~g/| where the paper prints 1 g/l, and 57 cells our committed page text cannot confirm. R3 caught it — which is the instrument working, not failing.

And my first result was wrong. I scored the Layout Parser 0 of 8, "no table found" on every page — because it returns tables nested inside the heading they sit under, with no plain text at all, and I read it like the Form Parser. One probe of the raw response found it. Read the response before believing the score.

Part 5 — Evidence for and against each option

Each option gets its strongest case first. The “against” list is the part that matters.

Option A

Docling, with the declared normalisations, as the extractor of record

Strongest case for
  • Local, free, offline. No key, no per-page cost, no recurring dependency — it fits the “no credential” posture exactly.
  • Its geometry is real: it de-interleaves Appendix 7 correctly and returns cell boxes.
  • 2 of 8 passes, the same as the cheap vision model — and the second one (Appendix 7) is the hard one.
Against
  • Marks no cell as a header on any page, so every table needs a convention or a review.
  • Returns nothing at all for two shapes (long cell, artwork).
  • 163–330 s for eight pages — slow, and 1.5 GB of install.
Option B

The vision model's lines form as a proposer, checked by the harness

Strongest case for
  • Best arm measured: 3 of 8, and it is the only arm that proposes dividers (Appendix 2).
  • Finds every table and gets header association right on 7–8 of 8 — Docling's worst failure.
  • Fast (5–10 s/shape) and cheap ($0.16 for eight pages). Nothing to install.
  • Its characters are never trusted: every cell is checked against the page, and failures are named.
Against
  • It writes text. Its remaining failures are exactly that: 70°C for the page's 70oC, re-wrapped lines, a paraphrased anchor.
  • Needs a key in the build path — a secret, and a network call per document.
  • Output is not reproducible in principle; the cache makes it re-scorable, not deterministic.
Option C

Buy a Google Cloud credential and measure Document AI

Strongest case for
  • It is the only candidate that supplies per-word geometry — the one thing §3.8 showed our committed text cannot give us.
  • Its schema has headers and spans as first-class fields, which is precisely what Docling lacked.
  • Money is not the argument: 8 pages now, a handful of documents a year.
Against
  • It is the same class as Docling (extractive layout + table model), so it inherits the four semantic failures nobody passed.
  • The geometry argument was its strongest card — and Docling has just cashed it by passing Appendix 7.
  • Costs a spending credential, four things that do not exist on this box, and a recurring hosted dependency.
Option D

No extractor: hand-author the blocks, review the 24 chunks, write the debt down

Strongest case for
  • Closes the two live defects immediately and honestly.
  • Needs nothing new: no tool, no key, no install.
  • The four unpassable shapes need a human judgement anyway — this is the only option that admits it up front.
Against
  • Generalises nothing. The next document needs the same review, and nobody will know that until it is late.
  • It is a decision to stop, and should be made explicitly rather than by exhaustion.

Part 6 — The rules that govern this

Not philosophy — the four repository rules that constrain any answer, and the one place they pull against each other.

RuleWhat it saysWhich options it constrains
Requirement 3 (R3) A cell must be a contiguous run of the printed page, in printed order. Rules out any arm whose characters are the model's own. This is why “grid only” is a separate verdict, not a pass.
Requirement 9 No new claim: a quote is a substring of the stored artefact. Rules out region-only citations — so Document AI's boxes would need a different claim, not a free upgrade.
Requirement 10 The gate needs no extractor. All four options survive: both instruments import with no tool and no key, and an evaluation is a build-time act with a recorded banner.
Claim discipline The public surface publishes only what we can verify. Argues against any pipeline whose output is plausible but unchecked — which is the vision model's whole failure mode.
Where the rules disagree

R3 demands the characters come from the page; the vision model's advantage is that it can see structure the page text cannot express. The anchors form was invented to satisfy both — boundaries from the model, characters from the page — and it is the worst performing form on the interleaved shape. The tie is broken by the evidence, not the principle: lines wins because a printed line is contiguous by construction.

Recommendation — and it changed twice today

Do not pick a tool yet. Check the key first (D83), then re-score. The arms differ by one or two shapes and the four shapes that separate them are the judgement ones, so choosing now would be choosing on a ranking we know is unreliable. Once the cells are judged: the Layout Parser v1.6-pro is the strongest on structure (8 of 8 tables, the long cell and Appendix 7 read correctly) and the vision model's lines form is the fastest and the only one that proposes dividers; Docling stays the offline fallback. Re-scoring all three costs nothing — every raw answer is cached.

What would change my mind

  • A tool that passes 6 of 8, or that passes any of the four semantic shapes without a human deciding.
  • S5's re-review of Appendix 6a and 7 taking more than a day — at that point a paid extractor is cheaper than the review, and Document AI is worth measuring properly.
  • A document we must ingest this quarter whose columns interleave — that needs per-word geometry, which is exactly Document AI's case.
  • Evidence that the vision model's character errors are systematic rather than occasional (a wrong digit that resolves as a contiguous run would be invisible to R3, and that is the one failure this instrument cannot see).
