Part 1 · What is actually true

Four paragraphs of plain language, then the eight pages the evaluation actually runs on. If you skip the rest of the page, read these.

1.1 What an "extractor" is, and why we would want one

Today the path from a PDF page to a citable table row runs through a person. pdftotext gives us a faithful wall of text; a human reads the printed grid and types it into the artefact as a <!-- table --> block: columns, rows, cells, empty cells, dividers. That is why the corpus is trustworthy, and why it cannot grow -- our table coverage is however many tables a person has transcribed: 44 rows, four documents.

An extractor is a program that reads the page's geometry and returns the table's structure: which text is a column label, which cells belong to which row, which cell is empty, which one spans two rows. Both tools below do that. Neither is free of consequences.

The three jobs that are welded together today

JobTodayUnder D80 (X2)

Verification -- proving the structure is the page'sthe same human, by eyeasserted: cell fidelity, row count, header association, spans
Citation -- what a quote isa substring of the artefact textunchanged: still characters we verified

S2 is only about the first job. The second was built last session (S4). The third never changes.

1.2 What Docling is

Docling is an open-source Python library that converts documents into structured data. You install it with pip, point it at a PDF, and it returns a document tree: sections, paragraphs, tables with rows and cells, and layout information. The parts that matter to us are its layout model (where on the page is each block) and its table-structure model (which cells group into a row, and which labels head which columns).

It runs here: no account, no key, no network at run time once its model files are on disk. The cost is the install: it brings PyTorch and a set of model weights, and the first run downloads those weights.

1.3 What Google Document AI is, and what "GCP credentials" means

Document AI is a Google Cloud service that reads documents for you -- a hosted version of the same idea. You send it a page (an image or a PDF page) and it returns detected text, layout, and for its Form Parser and Layout Parser processors, tables with headers, rows and spanning cells. There is nothing to install; the work happens on Google's machines and you are billed per page processed.

"GCP credentials" is how a program proves to Google that it may spend your money. Concretely, adopting it needs four things that do not exist on this box today:

#WhatWhy it is needed
1A Google Cloud project with billing enableda paid API with no billing account refuses to run
2The Document AI API enabled on that projectan API that is off returns a permission error, not a result
3A processor created in it (Form Parser or Layout Parser), which has a project id, a location and a processor idthat triple is what the code calls: which reader, in which region, on which project
4A service-account key: a JSON file with a robot e-mail address and a private key, granted a role that may call Document AIthis is the "credential" -- the secret the code authenticates with
The part that matters for our repo

A GCP key is a secret like GEMINI_API_KEY: it never enters git, never enters a committed .env, and it must be revocable. It is also a spending credential -- a leaked key is somebody else's bill. This repo already has a live example of the same trap: the dev box cannot refresh the corpus because GEMINI_API_KEY is absent, and a refresh without it writes NULL vectors that read "already ingested" forever.

Prices are per page and vary by processor and region. Do not quote a number from this page -- inferred and probably stale. For our scale -- 8 pages for the evaluation, a handful of documents a year afterwards -- the question is not the money, it is whether a recurring external dependency and a secret are worth it at all.

Measured last session, and it changes S2's protocol

A table's cells are only faithful against the extraction they were transcribed from. The landscape's tables pass every check against -table pages and report 10 violations against -layout. So S2 must record, per shape, which extraction mode the candidate read claims to come from -- otherwise the score is a coin toss.

Part 2 · The shape of the problem

Three asymmetries decide this more than any feature list.

2.1 S2 is a measurement, and a measurement is allowed to fail

The PRD already wrote its own falsifier: if the extractors lose spans or qualifiers on more than two of the eight shapes, then X3 (cite a region) moves first. That means a session spent on S2 can honestly end in "neither wins" -- and that is a result, not a wasted session, as long as it is written down. The failure mode to avoid is adopting a tool because it was installed.

2.2 The gate must never need the extractor

Requirement 10 of the PRD is blunt: the gate needs no extractor. The build machine and the CI gate do not have pdftotext today (they are given committed page fixtures for exactly this reason), so they will not have Docling or a Google key either. Whatever we adopt runs once, on a machine that has it, and the thing that enters the repo is the artefact, plus the recorded banner saying which extractor produced it.

That is also why "credentials" is a smaller question than it looks: a credential would be needed by the person running the evaluation, not by the product.

Part 3 · The options

Four, including the two nobody puts in a proposal: running both, and running none.

A · Docling first, and only then decide

1 installpip install docling in a throwaway venv; first run fetches models
2 readthe eight pages → its document tree
3 mapits table model → our TableRead
4 scoremismatches(case, read) per shape
5 recordone row per shape in the PRD; commit the runner

Every edge labelled: install feeds read, read is mapped to our shape, the shape is scored against S0's expectation, the score is written down. Steps 4-5 are already built.

B · Document AI first

1 accountproject, billing, API, processor, key yours to hold
2 calleight pages → Document AI response
3 mapits tables → our TableRead
4 scoremismatches(case, read) per shape
5 recordthe rows, plus a per-page cost line

Same instrument, different first step -- and that first step cannot be done by an agent on this box, because it needs a secret and a payment method only you can supply.

C · Both, in one session

Run A, then B on the same eight pages, and publish both columns. Justified only if the session has room for the install and the account; otherwise it produces two half-measurements and no decision.

D · Neither -- close the two live defects by hand and write the debt down

S5 without S2/S3: hand-review Appendix 6a's 20 rows and Appendix 7's 4 chunks into table blocks, so the harness sees them and the two defects close. No install, no account, no new dependency -- and no generalisation either: the next unseen document is still a transcription.

This is a real option, not a straw man

It closes the two defects the PRD measures, it is entirely within the rules, and it can happen in the same session as anything else. Its cost is that the PRD's goal -- "a document we have never seen can be ingested with its tables intact" -- stays unstarted.

Part 4 · Evidence for and against

The strongest case for each, then what is wrong with it.

A · Docling first

For
  • No secret, no billing, no account -- an agent can do the whole slice unsupervised.
  • The result is reproducible: same pages, same version, same output, forever.
  • It fails locally, where we can read the failure, instead of remotely.
  • If it wins, the build step stays offline -- which is what requirement 10 wants anyway.
Against
  • An install with model weights, on a laptop, for a measurement that may end in "no".
  • Its table model is younger than Google's; merged and spanning cells are exactly where young models lose.
  • It answers "can a local model do this", not "what is the best available".

B · Document AI first

For
  • Form and Layout parsers are the strongest published table structure available; spanning cells and headers are what they are built for.
  • No install, no local model drift, no Python 3.13 risk.
  • If our documents are the hard part, this finds the ceiling fastest.
Against
  • Four things you must create before one page is read: project, billing, processor, key.
  • A recurring dependency and a metered bill for a document set that changes rarely.
  • The evidence becomes "a response we received" -- harder to audit offline than a file we can diff.
  • It cannot be run by an agent at all, so the slice waits on you personally.

C · Both, and D · Neither

For
  • C: one comparison table settles the question for a year.
  • D: the two live defects close now, with no dependency and no secret; S5 becomes checkable.
Against
  • C: doubles the preamble, and one of the two preambles is yours.
  • D: the engine still does not generalise; the 45th table will be typed by a person too.

Where the rules point in different directions

The explore-skill rule ("run the strongest thing you can") points at Document AI; the repo's engineering rules point at keeping the pipeline local, reproducible and secret-free. I break the tie with a cost argument: the strongest thing you cannot run is not evidence. Docling can be run today, by me, and it answers the question that actually gates the next slice -- is a structure model good enough on these eight pages at all? If it is, we may never need the paid one. If it is not, the paid one is waiting and we will know exactly which shapes to test it on.

Part 7 · Recommendation

Run A, with B as the named second step -- and do not couple it to anything

Recommendation

Evaluate Docling first, on the eight pages, with S0's expectations and S4's checker. Publish the result as one row per shape in INGESTION_ENGINE_PRD.md, with a column for the extraction mode the read claims, and a seconds-per-page figure. Adopt nothing in that session: S2's deliverable is a table, and S3 is where a tool enters the pipeline.

Then: if Docling loses spans, qualifiers or header association on three or more of the eight, run B on exactly those shapes -- that is when a GCP project and a key become worth creating, and by then we have a list of the shapes to grade it on. If both lose on more than two, the PRD's own falsifier applies: X3 moves first.

In parallel, and independent of all of it: D is worth doing anyway -- hand-review Appendix 6a's 20 rows and Appendix 7's 4 chunks into table blocks, so the harness sees them and the two live defects stop being live. It is S5, it needs no tool, and it is the only option that improves the corpus today.

What this changes

Nothing in production. One install in a throwaway venv, one runner script, one results table, and a session record that says either "good enough, proceed to S3" or "here are the three shapes to take to a paid parser".

What would change my mind

  • You already have a GCP project and a Document AI processor. Then B first costs nothing new, and it is the stronger tool -- the argument for A collapses to "offline".
  • The install fails on Python 3.13 and a 3.12 fallback is not worth it. Then B, or D.
  • Docling's output keeps pictures and page images as blocks we cannot cite. Then the measure that matters is R7, and the honest answer may be "text extractors are not the whole answer" -- which is X3's argument, not a tool's.
  • A document arrives this week that must be ingested. Then D is the answer and S2 waits; the PRD says the same thing.
What I will not do without you

Create a Google Cloud project, enable billing, or hold a service-account key. Not because the paperwork is hard, but because it is a spending credential in a repo whose whole claim is that its evidence is checkable offline. If we go that way it should be a decision with your name on it.
