Interaction decision · the ask surface

What is the difference between a follow-up and a new question?

Not a wording question. A follow-up and a new question have to differ in five places under the interface — retrieval, the prompt, the cache, the escalation, and the board — or the two buttons are decoration.

The product already half-believes in follow-ups: every question is sent to the model with the last eight messages attached. But retrieval, the cache and the escalation all treat the same question as if it stood alone. That gap is where the bugs are.

Part 1 · What the code does today

Every question is a follow-up for the model, and a new question for everything else

Read off core/services/_chatbot.py at HEAD. The trace below is a reading of the code path, not a measured run — probe_chat.py is what would confirm which chunks come back.

LayerWhat it doesConsequence for a follow-up
Retrieval retrieve(text, standard_set) — the typed text, nothing else “What if I compost it first?” is searched as compost. Whether the right clause comes back is luck.
Prompt _history_for(session) — up to 8 messages, always, labelled “for context only” The model can see the earlier exchange, so it will answer from it — and cite a clause that is not in the retrieved set.
Citation audit All-or-nothing, over the retrieved chunks only That remembered clause is refused. So the follow-up either works by luck or refuses — and the refusal looks like a corpus gap.
Answer cache sha256(normalise(question)) + corpus fingerprint. No session, no history. A context-dependent answer is stored under a fragment and can be served to another visitor asking the same fragment about something else.
Escalation EscalatedQuery.question = text The administrator receives “what if I compost it first?” — unanswerable without the conversation.
Board A card is one question plus one answer A follow-up cannot become a card. A fragment is not a question anybody would search for.
Session control answer_question() takes no switch for history “Ask new question” cannot be built honestly today — the old thread still goes into the prompt.

The trace, in the order it happens

1
Turn 1: “Can I use cardboard from my neighbour?” Retrieves the Appendix 2 by-product row. The model quotes it. The audit accepts it. The answer is grounded and cached under that question.
2
Turn 2: “what if I compost it first?” Retrieval runs on compost. The eight-message history is attached. The model answers “yes, composting satisfies the condition” and cites the cardboard row.
3
If “compost” did not retrieve that row, the audit refuses the citation The answer is discarded, a refusal is shown, and an EscalatedQuery is written containing “what if I compost it first?”. Three separate things are now wrong: the visitor was told the documents cannot answer, the queue gained an unanswerable row, and the count of corpus gaps went up for a retrieval miss.
4
If it did answer, the answer is cached under the fragment Somebody else typing “what if I compost it first?” within the hour — about manure, or about straw — receives this answer. That is an answer from someone else's conversation.

The uncomfortable conclusion. Today, a follow-up is not a feature we chose; it is a leak in a design that assumes every question stands alone. The interface never asks the visitor which one they mean, because the system never had two behaviours to choose between.

Part 2 · The definition

One test, and three signals

The test: could this sentence be typed into the search box cold, by someone who had never seen the previous answer? If yes, it is a new question. If it only makes sense next to something else, it is a follow-up.

1. No subject of its own

what if I compost it first? — it has no meaning without turn 1. The subject is missing, not merely implied.

2. It points at the answer, not the topic

is that allowed for poultry too? — that refers to a sentence in the previous answer. No retrieval on this text can find the sentence.

3. It is short and shares a term

and for goats? — four words, one noun from the previous question. Short plus overlap is the cheapest machine signal there is.

Do not ask the visitor to classify their own question. They know least about what they are asking at the moment they choose. A visitor who wrongly picks “new” loses the context and gets a worse answer; one who wrongly picks “follow-up” gets an answer polluted by an unrelated passage — and, today, a cache entry under a fragment.

The interface should infer the mode and then show the inference, so the visitor can correct it with one edit. That correction is the “new question” control.

Part 3 · Three interfaces, one engine

The chrome differs; the behaviour must not

All three run the same scripted engine, so anything that looks different is the interface and nothing else. Ask the first question, then try a follow-up (“what if I compost it first?”) and a disguised new topic (“what about the annual fee?”).

Variant 1 · two buttons The visitor chooses the mode before they know what their question will be.
Following on from —

Starting a new question.

Answered together with the previous answer.

1 · Two buttons

  • Both actions are always visible, so nothing is hidden behind a mode.
  • It names the concept once, which teaches the visitor what the system can do.
  • Fails on its own terms: the choice is made before typing, and the two buttons compete for one action. Most visitors will hit the left one every time, which makes “new question” dead.

2 · Context strip

  • One primary action. The mode is a statement of fact (“following on from this”), not a prediction.
  • It shows which answer, so a visitor can see it is the wrong one and clear it.
  • The escape (“start fresh”) is a link, which is the right weight for something most visitors will never need.
  • Costs: the strip takes vertical space, and it must be rebuilt from the session or it lies after a refresh.

3 · Mode switch

  • It makes the mode explicit and lets the placeholder explain it (“ask about the previous answer” vs “ask anything”).
  • Two states to keep in sync, and the switch is set before typing — the same flaw as the two buttons, with more chrome.
  • Worse on a phone: a segmented control plus a textarea plus a button is a lot of tap targets above the fold.

The failure all three share, and the fix

  • None of them can tell that “what about the annual fee?” is a disguised new question.
  • Every variant therefore needs the same nudge after the answer: when the new answer shares no passage with the parent, say so and offer to ask it on its own.
  • That nudge is measurable, and it is the only honest way to admit the inference was wrong.

Part 4 · What has to change underneath

Five changes, and one that makes the rest work

ChangeWhy it is neededSize
A context parameter on the service
answer_question(..., context=…)		 So “new question” can actually drop the thread from the prompt. Today _history_for() always runs. Small: one parameter, one branch, three tests.
Rewrite the follow-up into a standalone question The only mechanism that fixes retrieval, the cache, the escalation and the board at once. One cheap model call with the last exchange as input. Medium: a second prompt, a 64-token cap, a fallback to the literal text on failure.
Retrieve on the rewrite, not the fragment “what if I compost it first?” becomes “If I compost the cardboard first, is it acceptable?” and the right row comes back for the right reason. One line, once the rewrite exists.
Key the cache on the rewritten question A standalone question is safe to share between visitors; a fragment is not. Two different fragments that resolve to the same question should share an answer. One line. Removes a cross-session defect rather than adding a feature.
Escalate the rewritten question, keep the fragment The administrator can only answer a question that stands alone. The fragment is context for them, not the question. Small: one field (or a prefixed store) plus the admin display.
Publish rewrites only A board card must be a question somebody could search for. “and for goats?” is not. Small: the publish action takes the rewrite, and shows it for approval first.

The rewrite is the load-bearing part. It is not a nicety for pronoun resolution — it is what turns a follow-up into an object that can be cached, escalated and published. Without it, every other change is either unsafe (a fragment in the cache) or useless (a fragment on the board).

It also gives the interface its one honest control: “Understood as: …”, editable. If the visitor edits it into a question that stands alone, they have asked a new question, and the system can see that.

What is deliberately not needed

  • No classifier. The same rule the PRD already applies to routing (G5): a short question that shares a term with the previous one is a follow-up. Failing that, treat it as new. Both mistakes degrade to today's behaviour.
  • No multi-turn retrieval (rewriting the query from the whole thread). Only the previous exchange is used. Eight messages of drift produce worse rewrites than one.
  • No stored conversation state beyond the session. The context strip is rebuilt from the last assistant message; clearing it sets one session flag.

Part 5 · The states that will happen

Six, and only one of them is the happy path

1 · A real follow-up

Compost after cardboard. Rewrite shown, retrieval on the rewrite, the answer cites the same row as the parent. The overlap with the parent's citations is the proof it was a follow-up.

2 · A disguised new question

“What about the annual fee?” Answered correctly, but its citation shares nothing with the parent. Show the nudge: “this answer doesn't use the earlier passage” and a one-click “ask it on its own”.

3 · A follow-up to a refusal

The parent is a gap, not a clause, so there is nothing to seed retrieval with. The rewrite still resolves “and in winter?”, and the answer will usually refuse again — so the escalation must attach the parent's gap id, or the administrator gets two unrelated fragments.

4 · A follow-up that refuses

Escalate the rewritten question, and keep the fragment beside it. An administrator answering “what if I compost it first?” is answering a question they were never asked.

5 · Publishing a follow-up

The tick to make a question public applies to the rewrite, and the visitor sees the wording before it is queued. Publishing the fragment would put “and for goats?” on the board.

6 · Coming back later

The strip is rebuilt from the session's last answer, so it survives a refresh. “Start fresh” is remembered for the session. On a published card, “Ask about this” seeds context from the card, not from whatever the visitor last typed.

Part 6 · Recommendation

One composer, an inferred mode, and a rewrite the visitor can edit

Use the context strip (variant 2). The visitor never picks a mode. The system infers it, shows which answer it is following on from, and shows the question it actually searched for. Editing that question is the way to say “this is something else”; “start fresh” is the explicit escape.

Why not the labelled pair. “Ask follow-up” and “Ask new question” describe a system state the visitor cannot see. A strip describes it for them. And naming it in two buttons teaches a distinction the visitor does not need to hold in their head — the product should hold it.

What survives from the pair: the words. The strip says “Following on from” and the cleared state says “Starting a new question”, so the vocabulary is still on the page, attached to the state instead of to a button.

What would change my mind

  • If rewrites are bad on real questions. Run the nine-question probe suite as follow-ups and compare: if more than one in five rewrites changes the subject, drop the rewrite and fall back to “seed retrieval with the parent's chunks", which needs no model call.
  • If follow-ups are rare. Measure the share of questions typed within 60 seconds of an answer. Under 10%, the whole mechanism is a cost for a rounding error and the honest product is one-shot questions with an explicit reset.
  • If the group wants the session to be a document. Then the follow-up chain should be printable as one record — which argues for keeping the exchange in the session and rendering it as a letter, not for anything in this page.
  • If the cache cannot be keyed on the rewrite for a reason I have not seen, key it on rewrite + parent hash instead. Same safety, slightly lower hit rate.

What I would not do: ship an “Ask new question” button before the service can drop history, or let a follow-up reach the cache or the escalation queue as a fragment. Both look like features and behave like defects.
