Part 2 of the follow-up decision

Is a rewrite the right instrument — and what builds the prompt next time?

Two questions that turn out to be one. The alternatives to a rewrite are only comparable once you separate what goes to retrieval from what becomes the canonical question. And you cannot choose between them by argument — you need a screen that shows the question, the passages, the prompt and the verdict.

Short version: the rewrite is for the ledger, not for retrieval. Retrieval can be fixed without a model. The last section is the console that lets you prove which one you actually needed.

Part 1 · The decomposition

One typed sentence feeds four things, and they want different texts

This is the whole argument in one picture. A “rewrite” is not one decision; it is a decision about which of these four gets the standalone text.

Typed question Turn 2: “what if I compost it first?”
->
1 · Retrieval query Wants nouns. This is the only consumer a rewrite has to serve, and the only one a model can improve on.
->
2 · Prompt Already gets the last 8 messages. Wants an instruction, not a rewrite.
->
3 · Ledger Cache key, escalation row, board card. Wants a standalone text that a stranger could search for.
a model can help here a convention is enough

Retrieval wants nouns the corpus contains. The ledger wants a question a stranger could have typed. Those are not the same test, and conflating them is what made my earlier recommendation look like one big mechanism. It is two: a retrieval fix, and a canonical-text convention.

The constraint that decides every option below: the audit is all-or-nothing over the retrieved set. A passage the model can see in the conversation is still inadmissible unless the retriever supplied it this turn. So any technique that encourages the model to lean on history must also put those chunks in the candidate set, or it converts a good answer into a refusal.

That single fact rules out one of the three ideas in the question, and it is the reason the cheap options below are shaped the way they are.

Part 2 · The alternatives

Seven ways to answer “what if I compost it first?”

Each row is judged on four things only: does it put the right passages in front of the model, does it survive the audit, does it produce a text the ledger can use, and what does it cost per follow-up.

On the two ideas in the question specifically

A
“Send the entire chain history instead of rewriting the newest question” This is option 1, and it is the natural first instinct because it needs no model. It fails for a measurable reason: significant_terms() picks terms by rarity and default_retrieval runs the rare-term arm first. From a two-turn chain the rarest term usually comes from turn 1 — cardboard — so the search answers the question you already had. Add the 8-passage budget split across two topics and the vector arm averaging two subjects, and the failure is structural, not a tuning problem.

But the instinct is right about one thing: the parent's nouns are exactly what the fragment is missing. Option 5 keeps them by gluing instead of synthesising, and option 3 keeps them as a second arm so they cannot crowd out the new intent.
B
“Append to the prompt: this is what the user asked, please answer the latest question” This is option 4, and it is the one the audit rules out on its own. Today the prompt already says “Conversation so far (for context only)”; saying it more forcefully changes which passage the model wants to cite, not which passages are available.

A model that obeys harder writes a citation for the clause it remembers from turn 1. The audit looks that clause up in this turn's retrieved set, does not find it, and refuses — all-or-nothing, by design (D47). So the instruction converts a lucky answer into a definite refusal.

It is still worth doing — after the candidate set contains the parent's clauses (option 2 or 3), where it becomes a useful precision nudge rather than a trap. Two lines, versioned, A/B-able in the console.

So: is the rewrite for the retrieval step? Yes and no, and the split is the useful part. It is the only option that fixes the retrieval query and produces a canonical text; but the retrieval half can be bought much more cheaply. What you are really paying the model for is the sentence a stranger could have typed.

Part 3 · Staging it

Buy retrieval deterministically. Rent the rewrite for the ledger.

Stage 1 — now, no model call

Context arm + carried citations + instruction.

Add a lexical arm over the previous question's rarest term and fuse it in, capped at two passages. Carry the parent answer's cited clauses in as a floor — the previous question's words are often in no clause at all, which is why the arm alone would not have fixed the cardboard case. Then the two-line follow-up instruction, now that a remembered clause is admissible.

Proves: whether follow-ups fail because of retrieval at all. If they stop failing, you never needed the model.

Stage 1b — the ledger, no model call

Composite canonical text.

Key the cache on parent_question + fragment instead of the fragment alone. Two visitors asking the same fragment about different parents get different keys and cannot collide; identical contexts share. The escalation row stores the same composite, rendered as “Can I use cardboard? → what if I compost it first?” — answerable by a human.

Proves: the cache leak was never a reason to call a model.

Stage 2 — only if the console says so

The rewrite, for the board.

When a follow-up deserves to become a card, the composite is not a title. At that point pay for the rewrite — or, cheaper still, have the administrator write the title from the composite. Either way it is a publishing decision, not an answering one.

Proves: the rewrite earns its call on the surface that needs prose, not on the one that needs nouns.

The honest revision

What I got wrong last time.

I said the rewrite was load-bearing for the whole mechanism. That was true only because I had not separated the four consumers. It is load-bearing for one of them. The staging above is the same conclusion with the cost removed from the critical path.

What would change my mind

  • If stage 1 leaves real fragments unfixed. The console should let you count them: follow-ups where the composite query still returns no clause the new intent needs. Above roughly one in five, the deterministic arm is not enough.
  • If the fused arm pollutes ordinary questions. A third arm on every turn is not free — it must only run when there is a parent, and the console must show it is not displacing good chunks.
  • If the group wants cards for everything. Then the rewrite moves to stage 1, because every good follow-up becomes a publishing candidate.

Part 4 · The instrument

The screen that decides all of the above

You cannot choose between these by argument, and you should not. The choice is settled by looking at twenty real turns. Here is what that screen needs to show, and what already exists to build it from.

What you asked forWhere it comes from todayGap
The question ChatMessage.content on the user row; the session UUID; the hashed IP None. (The rewrite, when added, needs its own field.)
The retrieved sections ChatMessage.grounding — locator, page, heading path, document, text sha — plus the retrieved_chunks M2M No rank, no arm, no score. RetrievedChunk has all three and they are dropped at persist time. A JSON field: no migration.
The prompt that got built Not stored — but build_prompt() is deterministic from the messages, the chunks and PROMPT_VERSION, all of which are stored None for new rows. Rebuild on demand; store prompt_version and a prompt digest so the console can say when a rebuild is no longer faithful.
The response citations.raw, citations.accepted, refusal_checks, content, tokens, latency, model cached is not stored; it is inferable (zero prompt tokens) but should be explicit.
Which corpus and which contract corpus_fingerprint, prompt_version None. This is what makes an old turn interpretable after an ingest.
The audit’s reason refusal_checks — the problems list, verbatim None, and it is the most under-used field in the model.

Why rebuild the prompt instead of storing it. A stored prompt is a copy that drifts from the function that produced it, and the first thing you want this console for is what would the prompt be today? Rebuilding calls the same build_prompt() the service calls, so there is one definition. The stored prompt_version and the text sha of each passage are what tell you whether the rebuild is still the same prompt.

Guardrails: staff-only, outside _public.PAGES like /uat/; it shows one visitor's question, so it is never linked from a public route; and a replay writes no rows — it is an experiment, not a turn.
